# spec-first-test

同じエージェントが実装とテストを書くと、テストが実装の分岐をなぞる。
この skill は、テストを書く側から実装の情報を構造的に遮断する。

遮断の対象は会話コンテキストではなくファイルアクセスである。
Agent ツールは subagent_type が fork のときだけ親の会話を継承し、それ以外は fresh agent として起動するので、
会話の遮断は普通にサブエージェントを呼べば済む。
残る漏れ口は、テストを書く側がテスト対象を探して実装ファイルを開くことだけになる。

## 適用範囲

seam 1 つを 1 サイクルとする。機能全体のテストを一括で書かせない。
仕様が薄い seam ほど、書かれるテストは想像上の挙動に寄る。

対象外は次の 2 つ。

- 実装済みコードへの後付けテスト。この手続きでは防げない
- 仕様が固まっておらず、実装しながら決めたい探索的な作業

## 1. 仕様を spec.md に書き出す

scratchpad に spec.md を作る。プロジェクトには置かない。

書く内容は、入力、出力、境界値、エラー時の挙動、副作用、前提条件。
書かない内容は、内部の関数名、データ構造、アルゴリズム、分岐の順序。

テストする seam をユーザーと合意する。合意していない seam のテストは書かせない。

先へ進む条件は 1 つだけ。
spec.md だけを読んだ人が、実装を見ずに期待値を独立に計算できること。
できないなら仕様が足りていないので、実装ではなく仕様を直す。

## 2. テストをサブエージェントに書かせる

Agent ツールで起動する。subagent_type に fork を指定しない。

渡すもの。

- spec.md のパス
- seam の import パスと公開シグネチャ。契約であって実装ではないので渡してよい
- テストフレームワークと、規約を合わせるための既存テスト 1 件

プロンプトに明示する禁止事項。

- 実装ファイルを読まない
- テストを通すための実装を書かない
- 期待値は spec.md の記述から導く。実装の計算手順を再現した式を期待値に置かない

## 3. red を確認する

書かれたテストを実行し、全件が落ちることを確認する。
落ちないテストがあれば、仕様が既存の挙動をなぞっているか、期待値がトートロジーになっている。
その場で直さず、理由を添えて 2 へ差し戻す。

## 4. 実装する

spec.md から実装する。テストコードは開かない。
手掛かりは、落ちたテストの名前とエラーメッセージだけに限る。
テスト本体を開いて期待値に合わせにいった時点で、この手続きの効果は消える。

テストのほうが間違っていると感じたら、直すのはテストではなく spec.md である。
仕様を更新し、2 からやり直す。

## 5. 忖度を検出する

green になったら実装を機械的に壊し、テストが落ちるかを見る。

- 境界の比較演算子を反転する
- 早期 return を 1 つ削除する
- 分岐の一方を無効化する

3 箇所試して落ちないテストは、実装をなぞっただけなので 2 へ差し戻す。
壊した箇所は必ず元に戻してからサイクルを終える。

## Codex に書かせる場合

codex exec に spec.md のパスだけを渡す。
git worktree で実装ディレクトリを分け、テスト用ワークツリーに実装を置かない。
同じリポジトリのまま渡すと実装を読むので、遮断はワークツリーで担保する。
