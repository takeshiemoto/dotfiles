# PR 本文の書き方

テンプレートに厳格に従う。これが核心。文体は常体。

本文は「なぜ変えたか（背景・目的）」と「何をしたか（変更の全体像）」をレビュアーの高さで書く。読み手は diff を読める前提なので、diff から読み取りにくい意図・全体像だけを補う。実装の過程・意思決定の経緯・作業ログ・検証ステータスは書かない。

叙述（背景・変更点・理由）の素材は `git log <base>..HEAD` と `git diff <base>...HEAD` だけ。実装中の会話（レビューを実施した経緯、別タスクの議論、設計判断の往復）は持ち込まない。log/diff に痕跡が無い情報は叙述には書かない（参照リンク節だけは例外、下記）。

## 短く書く（最優先・冗長さが最大の不満）

各節は最小限の行数で書く。説明的な段落を作らない。長いほど読まれない。

- 背景・目的の節（「PR を作成する理由」など）：内部機構を解説しない。ユーザー／レビュアーから見た問題か目的を、1行サマリ＋数項目の箇条書きで言い切る。「〜は単一選択の…なので、その結果…」のような仕組み説明は書かない。
- 変更点の節：観点ごとに1行。前置き・経緯・言い換え・正当化を足さない。
- 手順・参照の節（動作確認方法・関連 URL など）は無理に削らない。削るのは叙述（背景・変更点）の水増しだけ。
- 迷ったら削る。1文で足りるなら1文、箇条書きで足りるなら段落にしない。

## UI の変更は見た目を文章化しない

画面に見える変更は、見た目や画面遷移を文章で細かく描写しない。スクリーンショット（変更後・必要なら before/after）があればそれで足りるので、変更点の節は短い箇条書きに留める。スクショ添付は作者が行う前提でよく、貼れない分を文章で埋め合わせない。

## 構造を守る

- 構造を壊さない：見出し・節順・HTML コメントはそのまま。節を増減しない。
- diff から導けない節は捏造しない。ただし埋める材料があれば埋める：参照リンク節（関連 URL・設計/Figma・関連 Issue）には既知の関連リンク、手順節（動作確認方法・テスト手順）には diff から辿れる再現手順（必要な操作・経路）。これらは叙述ではないので素材限定の対象外。本当に材料が無い節だけ「なし」と明記し空欄放置もしない。ここで書くのは手順や参照であって、検証の合否・実施状況（「確認済み」「レビュー通過」）ではない。URL は捏造しない（確かに関連するものだけ）。
- チェックボックスは原則未チェック。チェックするのは `<base>..HEAD` の diff に対応する変更が実在する項目だけ（例：「テストを追加した」は diff にテスト追加がある時のみ）。判断材料が無い項目は未チェックのまま。

## 書く / 書かない

変更は観点（なぜ／何を）単位でまとめ、ファイル/行単位で書かない。

書いてよい：

- 何が変わったか（観点単位の全体像）。
- 制約・未完了の理由：なぜスタブか・なぜダミー表示か等、diff からは読めない非自明な制約。

書かない（＝実装過程・ノイズ）：

- 実装の細部の列挙：ファイル名・コンポーネント名・フック名・変数名・定数ファイル名・props・色。diff で読める。
- 設計選択の正当化：「〜の理由は」「〜に倣う」「〜に準拠する」など、どの実装手段を選んだかの経緯・言い訳。レビュー議論で扱うものであって本文ではない。
- 内部ドキュメント参照：ADR 番号など、この PR から辿れない参照（特に gitignore 等で含まれないもの）。
- 作業・検証の実施状況：型チェック・lint・レビュー実施済み、手元で動かした経緯。テンプレートに専用節がある時だけそこに簡潔に。
- 自明な機械的差分：呼び出し側追従・import 整理など。例外はファイル移動/リネームで import パス・モジュール名が変わる類だけ、探索コスト削減のため理由を書かず1行残してよい。

## バッククォートは最小限

識別子を機械的に全部囲まない。記号入りコード片や誤読箇所だけ、同じ語は初出のみ。

## バッドプラクティス：実装過程を書いてしまう

実際にダメだった例。意思決定の経緯・辿れない参照・検証ログを書き込んでいる。

```markdown
## 変更点
- 対象ユーザーカードは共有 UserInfoCard を流用せず feature 内に新規実装する。理由は ADR-0002（ピクセルパーフェクト保証と共有コンポへの波及回避）。
- マスク表示の暫定定数を `constants.ts` に集約し、無効化モーダルと詳細モーダルで共用する。

## 備考
- 型チェック・biome・CodeRabbit レビュー実施済み。指摘はプレースホルダ1件のみ。
- 設計判断は ADR（docs/adr）に記録しているが gitignore のため本 PR には含まれない。
```

何が問題か：

- 設計選択の正当化（なぜ共有コンポを使わないか、ADR-0002 の言い訳）＝本文の仕事ではない。
- `UserInfoCard` / `constants.ts` など実装の細部を列挙＝diff で読める。
- ADR-0002 はこの PR から辿れない（gitignore）。辿れない参照は書かない。
- 備考が検証ログ＝作業の実施状況であって変更内容ではない。

良い形（観点単位・diff から読めないことだけ）：

```markdown
## 変更点
- 発行済 API キー一覧から、キーの詳細を確認できるモーダルを追加した。
- 詳細モーダルから既存の無効化フローへ遷移できるようにした。
- 対象ユーザーの一部項目と各種日時は実 API 未接続のためダミー表示（差し替えは別タスク）。
```

## バッドプラクティス：背景・目的を長文で書いてしまう

実際にダメだった例。仕組みを説明する段落になっている。

```markdown
## PRを作成する理由
APIキー発行モーダルの対象ユーザー欄は単一選択のオートコンプリートで、候補から未選択のまま入力テキストが残っていても発行できてしまう。その結果、未選択のときは誤って必須エラーになり、選択済みのときはエラーなしで1人目だけが発行される。未確定の入力が残ったまま発行しようとした場合に…
```

何が問題か：内部機構（オートコンプリートの仕組み・状態）を説明している＝diff で読める／レビューで扱う話。背景・目的の節は問題か目的を端的に書く場所。

良い形（1行サマリ＋箇条書き）：

```markdown
## PRを作成する理由
2点のバグ修正
1. 複数指定時にエラーが表示されない
2. 未選択のまま発行した際のエラー文言が Figma と異なる
```

## バッドプラクティス：バグの原因をコード・内部機序で説明してしまう

実際にダメだった例。原因をコード片・例外文言・発生経路で説明し、用語で言い換え、弁明調で書いている。

```markdown
## PRを作成する理由
管理画面のユーザー削除の連打で500になる不具合の修正。

- 削除処理が同一ユーザーへの二重実行を想定しておらず、直列化されないまま両方が削除に進む（レースコンディション）。
- 1件目がマイフォルダと本体をソフト削除した後に2件目が進むと、`SoftDeletes` のスコープでマイフォルダを取得できず（結果が `null`）、「削除対象のマイフォルダが存在しません」の例外になる。
- この例外は素の `Exception` で `NotFoundHttpException` に変換されず500になる。

## 変更点
- 対象ユーザー行を `withTrashed()->lockForUpdate()` でロックして直列化し、削除済みなら `ModelNotFoundException`（404）を返す。
```

何が問題か：

- コード片・メソッド名・型名を本文に貼っている（`withTrashed()->lockForUpdate()`・`ModelNotFoundException` 等）＝差分の役割。原因・変更の説明にコードを書かない。
- 失敗の内部機序を細かく書いている（どのスコープで null になり、どの例外がどう変換されるか）＝レビューで扱う話。ユーザーに見える結果の粒度（連打で2件目以降が500）で止める。
- 弁明調（「想定しておらず」）＝欠けていた仕組みを事実で言い切る（「排他制御がない」）。
- 用語の言い換え（「（レースコンディション）」）＝補足を足さない。

良い形（結果と欠けていた仕組みだけ・コードなし）：

```markdown
## PRを作成する理由
管理画面のユーザー削除で、確認モーダルの削除ボタンを連打すると2件目以降が500になる不具合の修正。

- 削除処理に排他制御がなく、連打でほぼ同時のリクエストが両方とも同じユーザーの削除に入る。
- 1件目が削除を確定させた後に2件目が進むと、既に削除済みの状態のまま処理が進んで失敗し、500になる。

## 変更点
- サーバ側で削除対象の行にロックを取得して削除を直列化し、2件目は削除済みと判定して404を返すようにした。
- 削除確認モーダルの削除ボタンを送信中は無効化し、多重送信を防いだ。
```
