# ai-review

別ベンダーの 3 つのレビューと性能専任のレビューを互いの結果を見せずに走らせ、突合で見逃しと誤検知を減らす。このスキルはレビューだけを行い、コードは直さない。

## 0. 共通のゴールと指摘レベル

レビュアーは得意分野も観点も違うが、ゴールは 1 つだけで、プロダクト全体の品質を守ることである。
次の 2 つの文言を GOAL と LEVELS と呼び、すべてのレビュアーに同じ文言で渡す。突合と結論もこの GOAL と LEVELS で判断する。

GOAL:

```text
このレビューのゴールは、プロダクト全体の品質を守ること。担当分野の指摘を積み上げることではない。
自分の得意な観点から外れて見えても、プロダクトの品質を損なう欠陥なら指摘する。
観点の内側でも、品質を損なわないものは指摘しない。
```

LEVELS:

```text
指摘には次の 3 レベルのどれか 1 つを付ける。独自のレベルや数値の優先度は使わない。
重大な欠陥: 放置するとデータ破壊、情報漏えい、機能停止、誤った結果のどれかを招く。
品質上の問題: 実害は限定的だが、正しさ、性能、保守性のどれかを確実に損なっている。
改善提案: 欠陥ではないが、直すとプロダクトの品質が上がる。
```

## 1. 対象を確定する

- 引数にベースブランチがあれば、対象は `git merge-base HEAD <base>` からの差分。Codex のフラグは `--base <base>`、CodeRabbit のフラグは `--base <base>`。
- 引数がなく `git status --porcelain` が空でなければ、対象は未コミットの変更（ステージ済み、未ステージ、未追跡）。Codex のフラグは `--uncommitted`、CodeRabbit のフラグは `--uncommitted --include-untracked --base <現在のブランチ>`。CodeRabbit はリモートのないリポジトリでベースブランチを判定できずに失敗するため、`--base` を必ず付ける。
- 引数がなく作業ツリーがクリーンなら、レビュー対象なしと伝えて終了する。

基準コミットは、ベースブランチがあれば `git merge-base HEAD <base>` の SHA、未コミットの変更が対象なら `HEAD` の SHA とする。

対象の差分と未追跡ファイルの一覧を取得し、変更ファイル一覧と `git diff --numstat` の結果を手元に残す。

完了条件: Codex と CodeRabbit のフラグ、差分を再現するコマンド、基準コミットの SHA が 1 つに決まっている。

## 2. 秘密情報を確認する

差分と未追跡ファイルに次のどれかがあれば、Codex と CodeRabbit には送らず Claude 側だけで続行し、最終報告にその旨と該当箇所を書く。

- `.env` 系ファイル、`*.pem`、`*.key`、`id_rsa` などの鍵ファイル
- `-----BEGIN .*PRIVATE KEY-----`、`AKIA[0-9A-Z]{16}`、`gh[pousr]_[A-Za-z0-9]{36}`、`sk-[A-Za-z0-9_-]{20,}`
- `(api[_-]?key|secret|token|password)\s*[:=]\s*["']?[^\s"']{8,}` に一致し、プレースホルダーではない値

完了条件: Codex と CodeRabbit へ送るかどうかが決まっている。

## 3. レビューを並列で起動する

同じ応答の中で次の 4 つを呼ぶ。手順 2 で外部送信を止めた場合は Claude と性能だけを呼ぶ。

- Codex: Bash を `run_in_background: true` で `codex review <手順 1 のフラグ> "<GOAL と LEVELS>" 2>/dev/null` として起動する。GOAL と LEVELS は追加のレビュー指示として渡る。標準出力が最終レビューになる。
- CodeRabbit: GOAL と LEVELS を scratchpad の `review-goal.md` に書き出し、Bash を `run_in_background: true` で `coderabbit review --agent <手順 1 のフラグ> -c <review-goal.md のパス> 2>/dev/null` として起動する。`--use-credits` は付けない。出力は 1 行 1 JSON で、`"type":"finding"` の行が指摘になる。行番号は `codegenInstructions` の `at line N` から読む。`"type":"error"` の行が出たら、そのレビューは失敗として扱い、残りで続行する。
- Claude: Agent ツールで general-purpose のサブエージェントを起動する。プロンプトには GOAL、LEVELS、対象の差分を再現するコマンド、下記の出力形式だけを渡し、Codex や CodeRabbit の存在や結果には触れない。
- 性能: Agent ツールで general-purpose のサブエージェントをもう 1 つ起動する。プロンプトには GOAL、LEVELS、対象の差分を再現するコマンド、基準コミットの SHA、scratchpad のパス、下記の性能サブエージェントへ渡す指示だけを渡し、ほかのレビューの存在や結果には触れない。

Claude のサブエージェントへ渡す指示:

- 読み取り専用でレビューする。ファイルを変更しない。
- 差分全体と、変更箇所の理解に要る周辺コード、呼び出し元、テストを読む。
- この変更が持ち込んだ欠陥だけを指摘する。正しさ、セキュリティ、性能、保守性に実害があり、再現する経路をコードで示せるものに限る。実害の有無は GOAL で判断する。
- 指摘ごとに、LEVELS のレベル、`path:行`、欠陥の要約、発生する入力と結果、修正の方向を書く。セキュリティの指摘には分類（injection、XSS、SSRF、認可、秘密情報、その他）を付ける。
- 指摘がなければ、指摘なしと 1 行で返す。

性能サブエージェントへ渡す指示:

- 作業ツリーのファイルを変更しない。書き込むのは scratchpad の中だけにする。
- 差分から、変更されたシンボルを列挙する。対象は関数、メソッド、クエリ、スキーマとインデックス、キャッシュのキーと無効化、共有コンポーネント、設定値。
- 変更されたシンボルごとに参照を検索し、呼び出し元をエントリポイント（HTTP ルート、ジョブ、コマンド、画面）までたどって、到達するエントリポイントをすべて列挙する。変更が速くしようとしている経路を改善対象、それ以外を巻き添え経路と呼ぶ。
- 経路ごとに、変更前後のコストを次の単位で比べる。クエリと外部呼び出しの回数、入力件数に対するループの反復数、取得する行数とペイロードのバイト数、インデックスの利用、キャッシュの命中と無効化の範囲、ロックとトランザクションの範囲、バンドルサイズ、再レンダリングの回数。
- リポジトリに、作業ツリーを変えずに変更前後の両方で実行できる計測手段（ベンチマーク、クエリ数を数えられるテスト、ローカル DB への EXPLAIN、ビルドが出すバンドルサイズ）があれば計測する。`git worktree add --detach <scratchpad>/perf-base <基準コミット>` で変更前を用意し、同じ入力と同じ条件で両方を測り、終わったら `git worktree remove` で消す。回数とサイズは 1 回、時間は 5 回ずつ測って中央値を取る。
- 回数とサイズは、変更後が変更前より増えていれば悪化とする。時間は、変更後の中央値が 10% 以上遅く、5 回の最小値から最大値の範囲が変更前と重ならなければ悪化とする。
- 指摘するのは悪化した経路だけにする。指摘ごとに、LEVELS のレベル、`path:行`、経路のエントリポイント、悪化した単位と変更前後の値、計測済みか未計測かを書く。未計測の指摘には、入力件数に対する回数の式など静的に読んだ根拠と、計測に使えるコマンドを書く。
- 最後に、列挙したエントリポイントの一覧と、それぞれの判定（改善、変化なし、悪化、未計測）を返す。

起動したすべての完了通知が届くまで待つ。

完了条件: 起動したすべてのレビューについて、結果か失敗が揃っている。

## 4. 指摘を突合する

全レビューの指摘を、ファイル、行範囲、欠陥の中身で対応付ける。同じファイルで行範囲が重なり、同じ欠陥を指すものを一致とみなす。CodeRabbit の severity は critical を重大な欠陥、major を品質上の問題、minor 以下を改善提案として読む。

- 性能サブエージェントの計測済みの指摘: 変更前後の値を添えて採用する。
- 2 つ以上のレビューが一致した指摘: 採用する。レベルが食い違えば重い方を取る。
- 1 つのレビューだけの指摘: 指摘された `path:行` と周辺コードを自分で読み、発生する入力と結果を確かめる。確かめられたら採用し、確かめられなければ却下して理由を 1 行で残す。出どころのレビュアーが不得意な領域であることは却下の理由にしない。却下できるのは、GOAL に照らしてプロダクトの品質を損なわないと確かめられたときだけ。

完了条件: 全指摘が採用か却下のどちらかに分類され、却下には理由がある。

## 5. security-review への昇格を判定する

次の条件のどれかに当たれば、ユーザーに `/security-review` の実行を勧め、当たった条件を示す。`/security-review` は非対話で実行できないため、このスキルからは起動しない。

- A 変更パス: `auth`、`payment`、`migration`、`middleware`、`Dockerfile`、`.github/workflows/`、`*.sql`、ロックファイル（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`bun.lock`、`Gemfile.lock`、`poetry.lock`、`uv.lock`、`Cargo.lock`、`go.sum`）を含む
- B 追加行の内容: 暗号処理、SQL 文字列の連結や埋め込み、`innerHTML`、`dangerouslySetInnerHTML`、デシリアライズ（`pickle.loads`、`yaml.load`、`unserialize` など）、`eval`、`exec`、`child_process`、`subprocess` を含む
- C 規模: 変更ファイルが 20 を超える、または追加行が 1,000 を超える
- D 採用した指摘: injection、XSS、SSRF、認可、秘密情報のどれかに分類されるものがある
- E 判定の食い違い: 1 つのレビューだけが重大な欠陥か品質上の問題のセキュリティ指摘を出し、ほかのレビューが同じ箇所に何も出していない

完了条件: A から E のそれぞれに当否が付いている。

## 6. 結論を報告する

結論は次の順で最初に当たったものにする。

- block: 採用した指摘に重大な欠陥がある、または D に当たる
- fix: 採用した指摘に品質上の問題がある
- pass: 重大な欠陥も品質上の問題もない。採用した改善提案だけがある場合と、指摘がない場合の両方を含む

報告には次を含める。

- 結論と対象（ベースブランチか未コミットか）
- 採用した指摘: レベル、`path:行`、要約、出どころ（指摘したレビューの名前をすべて）。重大な欠陥、品質上の問題、改善提案の順に並べる
- 性能の指摘には、経路、変更前後の値、計測済みか未計測かを添える
- 性能サブエージェントが列挙したエントリポイントの一覧と判定
- 却下した指摘と理由
- 当たった昇格条件と `/security-review` の推奨。当たらなければ省く
- 手順 2 で Codex と CodeRabbit を外した場合、または手順 3 で失敗したレビューがある場合はその旨
