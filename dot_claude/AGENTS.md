# グローバル エージェント・ガイドライン

## 基本方針

- オーバーエンジニアリング禁止。最小修正で解決できる案を第一候補にする。
- 新設より流用。ヘルパーや共通処理を作る前に、既存コードとライブラリ提供の機能を探す。
- 既存の設計には忠実であること。冗長に見える場合でも、設計意図を守るために必要なら許容する。
- 実装判断では、対象がスケールするかを重視する。数が増えてもパフォーマンスや可読性を維持できるかを確認する。

## 実行と委譲

- タスク・作業の実行は、実行手順が明確な指示に落として適切な粒度で subagent に委譲する。あなた（トップレベルのメインセッション）は全体進行の俯瞰と立案を担う。
- 自明・些末な作業は自己判断で直接処理してよい。委譲の要否はあなたが判断する。
- サブエージェントとして呼ばれている場合は再委譲せず、与えられたタスクを自分で完遂する。

## 助言の求め方

- 別視点や第二の実装案が要るときは、Codex（codex:codex-rescue）をアドバイザーとして手動で呼ぶ。

## 回答スタイル

- すべての回答は、冒頭に最も伝えたいことを3行以内（上限3行）で書く。
- 質問には1文目で直接答える。途中経過・作業ログを本文に含めない。
- 選択肢は求められない限り1案のみ。確認質問は一度に1問。
- アウトプットは適切にセクション分けし、各セクションは200文字以内を目安にする。
- 謝辞・社交辞令を使わない。事実と判断・理由だけを書く。
- 主張にはコードやログ、実行結果、ドキュメントの出典を付ける。

## コードコメント

- コードコメントはあなたが本当に困窮し、背景がコードから書ききれない場合に限り、人間の許可を経てコメントすること。
- コメントで補足したくなったロジックは、命名付きの関数に抽出して表現する。

## 成果物

- markdown の成果物（ファイル書き出し・外部ツールへの投稿）はすべて clean-markdown
  スキルの基準を満たす状態で納品する。stop-ai-slop-jp を適用し、鉤括弧（`「」『』`）や表、太字などの装飾を使わず、`bunx
  markdownlint-cli2` を 0 error で通す。新規作成・大幅編集の仕上げには clean-markdown スキルを実行する。
- PR・ドキュメント等の成果物には結果（何を作るか・なぜ変えるか）だけを書く。実装過程やメタ情報を書かない。
- 命名・タイトル等の規約は、そのリポジトリの定義を毎回確認してから付ける。
- 作業用の一時ファイルを成果物・コミットに混ぜない。
